1. Executive Summary

Lumina Agent는 단순한 대화형 UI나 기능 시연물이 아니라, 사내 AI 실행을 재현·통제·복구·감사하기 위한 Agent Operating Layer를 지향하는 실질적인 Alpha 제품입니다.

2. 서론: 제품의 의미와 평가 관점

본 제품의 가치는 “또 하나의 ChatGPT 화면”에 있지 않습니다. 조직 내 여러 AI Provider와 파일·지침·Memory·Skill·MCP·Tool·산출물을 하나의 실행 계약으로 묶고, 누가 어떤 권한과 버전을 사용해 무엇을 수행했는지 복원하는 데 있습니다.

핵심 포지셔닝
사내 여러 LLM을 단일 업무공간에서 사용하고, Skill·MCP·업무지침을 조직 자산으로 버전 관리하며, 장시간 Agent Run과 산출물을 안전하게 실행·복원·감사하는 플랫폼.

따라서 평가는 화면의 완성도보다 다음 질문에 초점을 맞췄습니다.

  1. 설정과 상태값이 실제 서버 정책으로 강제되는가?
  2. 사용자·Project·대화·파일의 격리가 모든 조회·검색·실행 경로에 일관되게 적용되는가?
  3. 서버 중단·재시도·동시 요청에도 중복 부작용과 데이터 손상이 방지되는가?
  4. 외부 Provider·Web·MCP로 반출되는 데이터가 조직 정책에 따라 통제되는가?
  5. 생성된 파일과 HTML을 비신뢰 입력으로 취급하는가?

5. 테마별 잘한 점과 개선할 점

5.1 제품·도메인 설계

잘한 점

  • Project를 파일·지침·Memory·확장의 격리 경계로 설정
  • Run에 Provider·Model·지침·Skill·MCP·파일 버전을 고정
  • 브라우저가 아니라 Backend가 실행을 소유
  • 사내 업무에 필요한 관리자·감사·Marketplace를 초기부터 고려

개선할 점

  • Stable/Beta/Experimental/Planned 기능이 README에 혼재
  • 연구 문서가 모두 현재 필수계약처럼 작동해 범위가 계속 팽창
  • 공유 Project 타입은 모델에 있으나 생성·전환 Workflow가 없음
  • 기능 범위가 핵심 Golden Path보다 빠르게 확장됨

5.2 Agent Loop·Run 내구성

잘한 점

  • 중앙 Run 상태머신과 불가능한 전이 차단
  • DB Event가 원본이고 Process Broker는 깨우기 힌트로만 사용
  • Worker 종료 후 Queue 복구와 부분 Draft checkpoint
  • 실행 중이던 외부 Tool의 결과 미확정 시 자동 재실행 금지
  • 완료된 Tool 결과와 Run snapshot을 재사용

개선할 점

  • 시간·Token·비용·Turn 제한이 실제로 적용되지 않음
  • Worker lease·heartbeat·execution epoch 부재
  • Event sequence 증가가 다중 Writer에서 원자적이지 않음
  • 동시 Tool 승인 처리 시 Run이 awaiting_approval에 고착 가능
  • ToolExecution idempotency key가 대부분 비어 있음

5.3 인증·권한·공유

잘한 점

  • Argon2 비밀번호 Hash와 필요 시 Rehash
  • 존재하지 않는 계정에도 Dummy 검증을 수행해 Timing 차이 축소
  • Session·CSRF 원문을 DB에 저장하지 않고 Hash만 보존
  • 계정 비활성화·비밀번호 초기화 시 Session 폐기
  • 공유 Token 원문 미저장, 로그 경로 마스킹, 동일 404 응답

개선할 점

  • Project 구성원이 다른 사용자의 private 대화를 읽고 수정할 수 있는 권한식
  • Composer·Artifact·Attachment 조회도 Project 범위로 과도하게 열림
  • 개발용 고정 관리자 계정이 운영환경에서도 생성
  • 비밀번호 최소 길이 1, must_change_password 실질 미강제
  • 공유 링크가 로그인·수신자 제한·기본 만료 없이 누구나 접근 가능
  • Project member가 Project 보관 등 관리 작업까지 수행 가능

5.4 Provider·네트워크·데이터 반출

잘한 점

  • Provider별 Adapter 경계와 Model catalog 승인 절차
  • 회사 CA와 Public CA를 결합하고 TLS 검증 우회 금지
  • 공용 Web의 Redirect·Private IP·DNS rebinding 방어
  • 외부 콘텐츠를 데이터로 명시하고 Prompt Injection 경계 문구 사용

개선할 점

  • 사내 Provider 기본 주소가 평문 HTTP로 인증값과 Prompt 전송
  • Project 데이터 등급 × Provider trust level 정책 부재
  • User/Project Memory가 외부 Provider로 자동 포함될 수 있음
  • Read Tool의 query·URL에 내부 원문을 넣어 외부 반출 가능
  • 공개 코드에 회사 Endpoint·인증 Envelope·내부 시스템명이 포함

5.5 Skill·MCP·Tool 승인

잘한 점

  • Working Draft와 공개 Version을 분리하고 Run이 정확한 digest를 고정
  • Secret 파일·inline Secret·Token 패턴을 게시 단계에서 차단
  • MCP exact host allowlist, HTTPS, IP pinning, DNS 재검증
  • Shell 대신 create_subprocess_exec 사용
  • 승인 객체에 Tool·effect·risk·argument digest를 보존

개선할 점

  • MCP 위험도를 Tool 이름의 get/read/delete 등 단어로 추론
  • 읽기 Tool도 외부로 데이터를 전송할 수 있으나 별도 egress 분류 없음
  • npx·uvx 허용은 실행 시 Package 다운로드와 원격 코드 실행 가능
  • stdio MCP가 서버 OS 계정으로 실행되어 논리 권한을 우회 가능
  • 승인 UI가 실제 수신자·대상·내용을 충분히 설명하지 못함
  • yolo 모드는 사내 운영에서 과도한 권한

5.6 파일·Artifact·브라우저 안전성

잘한 점

  • Project File 경로 정규화·Hash·Immutable Version·CAS
  • DB 충돌 시 저장 파일 정리와 추출물 cleanup
  • OpenXML ZIP bomb·Macro·외부 Relationship·구조 검사
  • XLSX 수식형 모델 텍스트를 문자열로 강제해 Formula Injection 방지
  • Artifact 공유 시점의 Version과 Hash를 고정

개선할 점

  • Artifact 저장은 Project File보다 DB/Storage 원자성이 약함
  • Orphan blob·오래된 Draft·삭제 파일 Garbage Collection 부재
  • HTML 편집 iframe의 allow-scripts + allow-same-origin 조합 위험
  • 직접 작성한 HTML Sanitizer가 CSS·SVG·외부 Resource를 완전히 다루지 못함
  • 입력마다 전체 HTML을 postMessage하여 대형 문서에서 성능 저하
  • 첨부 문서 추출이 API 요청에서 동기 실행되어 자원 고갈 가능

5.7 Frontend·API 계약·코드 품질

잘한 점

  • ReactMarkdown skipHtml, 안전한 링크 변환, Mermaid strict mode
  • 중단된 SSE를 Snapshot과 sequence로 복구하는 UI 구조
  • Run/Tool/Plan/Artifact 상태를 사용자에게 가시화
  • 공통 디자인 토큰과 비교적 일관된 업무형 UI

개선할 점

  • App.tsx 약 3,680줄, executor.py 약 3,499줄 등 책임 집중
  • Frontend API·Type 약 2,800줄을 수작업 관리
  • 대부분의 FastAPI Route가 response_model을 사용하지 않음
  • Frontend 단위·통합·E2E 테스트 부재
  • API 계약·Migration·호출 수가 기능 추가 후 쉽게 드리프트

5.8 운영·배포·관측성

잘한 점

  • Windows 설치기에서 의존성·Migration·Build·CA·진단을 일관되게 처리
  • 비밀값을 명령 오류 메시지에 재출력하지 않으려는 방어
  • Health live/ready 분리와 구조화 요청 로그
  • 감사 이벤트 범위가 넓고 민감 Key 재귀 Redaction 적용

개선할 점

  • CI, Container, Linux 운영 배포 Manifest 부재
  • 실제 PostgreSQL 동시성·Migration 통합 테스트 부족
  • Audit log append-only·외부 SIEM·보존 정책 부재
  • 사용자 데이터 삭제·보존·Orphan cleanup 정책 미완성
  • Root License와 제3자 Vendor 라이선스 정합성 확인 필요
  • 임시 검증 이미지가 저장소에 포함

9. 결론

짧은 개발 기간과 AI 중심 구현이라는 조건을 고려하면 제품 방향, 상태 모델, 복구 설계, 확장 버전 관리의 수준은 매우 높습니다. 특히 Worker 중단 후 복구, Tool의 미확정 부작용 비재실행, Run Snapshot, MCP 네트워크 방어는 일반적인 초기 프로젝트의 범위를 넘어섭니다.

반면 현재 가장 큰 문제는 기능의 부재가 아니라 정책 표현과 실제 강제의 간극입니다. private, visibility, limit, idempotency 같은 필드와 설정이 존재하지만 모든 실행 경로에서 동일하게 집행되지 않습니다. 이 간극은 다중 사용자와 실제 회사 데이터가 들어오는 순간 보안사고·과금·데이터 손상으로 확대될 수 있습니다.

최종 권고
신규 기능 개발을 잠시 동결하고 P0·P1을 완료한 후 3~5명의 제한된 사용자에게 Golden Path 중심으로 배포하십시오. 기능 개수 대신 “하나의 실제 업무가 권한·근거·복구·산출물까지 안전하게 끝났는가”를 성공 지표로 삼는 것이 적절합니다.
